# Decision log

New decisions go at the end of the relevant table with the reason. Decisions carried over from the
earlier prototype ([jhj1012/kiosk-ai](https://github.com/jhj1012/kiosk-ai)) say so.

## Product

| Area | Decision | Reason |
|---|---|---|
| Interaction | **Voice only**, through a telephone-style handset (mic at the mouth, earpiece at the ear). No touch buttons. | The idea we demo. A handset also keeps the customer's voice close to the mic and the assistant's voice away from it (less echo, better barge-in). |
| Session start/end | Lifting the handset (off-hook) starts a session; hanging up (on-hook) ends it and clears the order. | Clear, physical start and end of each customer; no guessing who the next customer is (the old prototype needed timeouts and a "new customer?" question for that). |
| Hook switch | Simulated with the Space key in the display, behind a `HookSwitch` interface. | The hardware does not exist yet; a USB handset or microcontroller can replace it without touching the rest. |
| Assistant | Built into the kiosk: it knows the whole menu and flow and acts through function calls. | Replaces the old design (an external assistant reading another app's screen through Windows UI Automation), which was slow and fragile. |
| Display content | **The assistant decides what the screen shows**: display functions take any set of items and a heading (e.g. allergy-safe items), plus item details and cafe-info cards. | Requested by the team: the screen should follow the conversation. Allergen filtering is done by code from the data, not by the model. |
| Menu data | Same items, prices, option groups and option prices as the old prototype, now in `data/menu.yaml` with Korean descriptions, ingredients and tags (recommended, caffeine, sweetness, allergens). Option groups are marked required (temperature, size) or optional. Unchecked facts carry `verified: false`. | YAML allows comments and is easier to edit by hand than JSON. Invented demo facts must be easy for the team to find and review. |
| Required vs optional options | Required options (temperature, size) must come from the customer, asked one at a time. Extras (shots, syrups, toppings, tumbler) are asked once, for the order's **first** drink only ("추가하실 거 있으세요?", the screen lists them); later drinks get them only when the customer asks. | Required choices must come from the customer. Extras: team feedback after milestone 8, then "only the first drink" (2026-10-26) to keep orders short. |
| Discounts and stamps | **Dropped** for the demo. | Stamps need a phone number, which the customer would have to say out loud in a café; coupons add a flow with little demo value. Possible later features. |
| Payment | Simulated: "카드를 단말기에 꽂아 주세요" → "결제 중..." → done with an order number. | Demo, no real terminal. |
| Language | Korean (customers); code, docs and model instructions in English. The README's guide for teammates is in Korean, its developer part in English. | Carried over. Teammates read the README first; most of them do not program. |

## Technology

| Area | Decision | Reason |
|---|---|---|
| Language | Python 3.12 | Carried over: the team knows Python; old modules (cart logic, audio, Gemini client) can be reused. |
| Package manager | `uv` + `pyproject.toml` + `uv.lock` (uv's own Python: `python-preference = "only-managed"`) | Carried over: identical dependency versions for every teammate. |
| Voice conversation | **Gemini Live API**, one streaming session per customer: audio in/out, built-in voice detection and interruption (barge-in), transcripts of both sides, function calling. Model `gemini-3.8-live` (stable, Google's default for voice agents; `gemini-3.8-live-extended-thinking` is tested as an alternative). | Replaces the old pipeline (separate Gemini speech-to-text call + agent call + Windows SAPI voice), which needed several requests per turn against the free tier's ~15 requests/min, could not be interrupted, and had several seconds of latency. **Verified in milestone 3** ([live-check.md](live-check.md)): ~1.2–1.6 s from the end of speech to the first audio, barge-in in ~0.4 s, function calls reliable apart from rule slips that code checks catch. The extended-thinking variant was rejected: its function calls come ~10 s late. |
| Actions | Function calling (Live API), with flat enum parameters. | The Live API's way to act. The old prototype preferred schema-constrained JSON because *local* models broke tool calls; milestone 3 measures function-call reliability with Gemini Live. |
| Safety | Safety rules live in code: pay only after the customer asked to pay (in their own transcribed words) and the order and total were read back with the cart unchanged since; clear the order only after the customer's confirmed yes (hanging up is the exception). No extra "결제하시겠어요?" question: the read-back is a statement. | Carried over: in the old prototype's tests, prompt rules alone were not enough (the model pressed a button that emptied the cart to "go back"). |
| Voice detection and transcription | Server voice detection with `start_of_speech_sensitivity: HIGH` and `prefix_padding_ms: 300`; input transcription with `language_codes: [ko-KR]` and the menu names as `custom_vocabulary`. | Measured in milestone 3: with the defaults, short answers ("레귤러요") were missed, first syllables were clipped and transcripts sometimes switched language. |
| Typed input | `send_realtime_input(text=...)` into the same Live session. | Faster than `send_client_content` (median 1.2–1.5 s vs 2.25 s to the first audio) with the same results. Typed text interrupts the assistant like speech does. |
| Payment flow | One `request_payment()` call: code checks that the customer asked to pay, shows the review and returns a read-back written by code; **code starts the card terminal** after the assistant's spoken turn contains the total. Replaces the planned `review_order` + `start_payment` (milestone 4). | In the milestone 3 check the model said the read-back but forgot `start_payment` in 4 runs, and once started the payment unasked. Now the model cannot skip or rush the step. |
| Required options: no guesses | **Redesign (2026-10-26)**: the text check that set a temperature or size only if the customer said that choice is gone. An answer to the question on screen is always taken, whatever the words. Only a guess is left out: a required option the customer did not mention at all (none of the option group's `words` in `menu.yaml`) while the screen was not asking for it; the kiosk then asks. | The old check refused misheard answers ("라디오" for 라지요) and answers recorded a few turns late (the 18:05 log), so questions were repeated. Without any check, the first spoken run showed guesses (size=regular for "아메리카노 세 잔, 하나는 차갑게…", temperature=ice for "카페라떼 하나 주세요"). |
| Voice | `Sulafat` (prebuilt Live voice). | Picked by the team from eight samples (milestone 3). |
| Transcription language | Input and output transcription with `language_codes: [ko-KR]`; pieces mostly in another script are dropped from the transcript. | Once, a Hindi paragraph was appended to the transcript of a Korean greeting; never shown to customers. |
| Session limits | One Live session per customer; session resumption, `GoAway` handling and context compression; on a restart the new session gets the current order. | Live connections last ~10 min and audio sessions 15 min; an order takes 1–3 min. |
| Audio I/O | In the backend with `sounddevice`; handset devices chosen in `configs/settings*.yaml` by name or index. 16 kHz in, 24 kHz out. | The API key and audio stay out of the browser; no browser mic permissions; reuses the old device code. Risk: echo from the earpiece into the mic; measured in milestone 7 (an energy gate while speaking if needed). |
| Backend server | FastAPI + uvicorn, one WebSocket; serves the built display. | Small, async (fits the Live session), easy to test without a network. |
| Display | Svelte 5 + TypeScript + Vite; Svelte's built-in transitions (`crossfade`, `flip`); Pretendard font bundled. Full-screen with Microsoft Edge `--kiosk`. | Clean, smooth animations without a motion library; Edge is on every Windows 11 PC (no pywebview). The display only renders state pushed by the backend. |
| Display layout | **Portrait** (1080×1920; a centered portrait frame on landscape monitors), white with soft blue gradients, flat (no shadows), minimal: the start screen is only the assistant and one sentence. Sizes in `rem`, 1/120 of the height. | Team feedback on the first version (milestone 5): it should be vertical, less warm, whiter, with fewer things on screen. |
| Display motion | **One continuous page** instead of screens: the assistant and the conversation stay at the top, the order at the bottom; content appears and disappears in place (cards `flip` to new places, a card's image grows into the item, an added item flies into the order bar). `prefers-reduced-motion` turns animations off. | Team feedback: moving between screens felt like page changes. |
| Choices over the avatar | Everything is a **list** (menus, kinds of menu, options), shown over the avatar's chest, and only what the assistant is asking now: while choosing an item, one option group at a time, earlier choices as chips. No menu descriptions on screen (the assistant tells them). Three backgrounds to compare: blur, a gradient from the bottom, boxes. | Team feedback: lists are clearer over a character than cards, and one question at a time matches the conversation. |
| Ordering steps | **Redesign (2026-10-26)**: the kiosk keeps one **current question** (here or to go, a drink's next required option, the first drink's extras, what else, the staff question, the read-back), decided from the state. Every function result says it (`ask`) and the screen shows it, so they cannot disagree. Answers may be about any drink: functions are named by what they change (`order`, `set_options`, `change`, ...), and one sentence may need several calls in the same turn. 17 functions became 11. | Team feedback: the screen and the question sometimes disagreed and questions were repeated, because rules had been added one by one in several places. Rules: [conversation-rules.md](conversation-rules.md); design: [conversation-design.md](conversation-design.md). |
| Going back | One `go_back` for every screen, each option question included; `go_back(to)` jumps to the latest screen of an item. It shows the view from the current state (choices already made stay marked; a drink added since comes back as its order line, to change with `change`) and never changes the order. Replaces `edit_line`. | Team feedback: a single back that works everywhere, also from the size question back to the temperature question. |
| Requests the kiosk cannot do | Passed on to the staff (`note_for_staff`): "네, 알겠습니다. 해당 사항은 직원에게 전달하겠습니다." instead of "불가능합니다". Before the read-back the assistant asks once "직원에게 따로 전달할 말씀 있으세요?" (enforced by `request_payment`). Notes appear in the review and with the order number. | Team feedback: refusing reasonable requests ("아메리카노는 포장, 카페모카는 매장에서") feels bad; a person at the counter would just pass them on. |
| Hesitation and speech not for the kiosk | `stay_quiet` is always offered: hesitation ("음…", "어…", "잠깐만요") gets no answer and the kiosk never speaks up on its own. A developer-panel switch (off by default, from the next customer) extends it to talk to someone else. When the model calls it, the turn is muted in code and the words count for nothing. | Team requests. Measured ([live-check.md](live-check.md)): Google's proactive audio ignored nothing and an instruction alone made the model say odd things; the function ignored 14 of 15 and answered all 15 real requests. |
| Wording | Temperature is always 따뜻하게 / 차갑게 (따뜻한 / 차가운 before a name; never 아이스 / 핫): `say` in `menu.yaml` is what is said, the new `label` what the screen shows. An option is asked by its name only ("사이즈는 어떤 걸로 해 드릴까요?"), without reading choices or prices, which the screen shows. | Team test feedback: mixed words, and reading out "라지는 500원 추가" took time for nothing. |
| Printed menu board | A menu board hangs next to the kiosk: after here / to go the assistant says "메뉴판에서 메뉴를 고르신 뒤 말씀해 주세요" (also on screen), and refers to the board instead of reading menus. | The demo will have a printed menu; customers choose from it. |
| One item, different options | "아메리카노 세 잔, 하나는 차갑게 두 잔은 따뜻하게": one `choose_item` per part; the same item already waiting is split (or updated) instead of replaced. When it waits more than once, the options in an answer say which part it is for. | Team test: the cold one disappeared. |
| Hearing whole sentences | The voice detection waits longer at pauses (`end_sensitivity: low`). (Aliases for misheard sizes are no longer needed: options are not checked against the words.) | Team test: sentences were cut at short pauses ([live-check.md](live-check.md)). |
| Subtitles | Off by default; a switch in the developer panel. | Team feedback: the avatar talks; text on top is noise. Useful for testing. |
| Display settings | Background style, subtitles and every main colour are set in the developer panel and **saved by the backend** (`configs/display.local.json`, git-ignored), which sends them to every display. | Full-screen mode (`--kiosk`) uses its own Edge profile, and another PC or browser would start empty; settings saved in the browser would not reach them. |
| Showing menus | When asked what there is, the assistant shows 3–5 recommended items without a heading and asks whether to show other menus; then the kinds of menu (`show_categories`), then the chosen kind. At most five items at a time, unless it is a whole category. | Team feedback: too many menus at once. Fewer items per step suit a voice conversation. |
| Fake events | `scripts/make_demo_events.py` records demo timelines by driving a real `Kiosk` and the server's event builders (`kiosk/server/events.py`); the display plays them with `?demo=...`; a test fails when they are out of date. | The display is built and checked against the real event format before the backend is wired (milestone 6). |
| Handset audio | `sounddevice` in the backend: the microphone streams 20 ms frames into the session while a customer is on the line; the earpiece plays from a buffer that is cleared at once on an interruption or hang-up. Devices by name in the settings (MME on Windows converts rates; others are resampled with numpy). The animation follows what the earpiece really plays. | As planned: the key and the audio stay out of the browser. Tests use a fake `sounddevice`. |
| Phone mode | An Android phone can be the screen, with the handset plugged into it (`--phone`, `Start Kiosk (phone).bat`). The laptop runs the backend and serves the phone over its hotspot with HTTPS (a self-signed certificate it makes itself); the phone streams its microphone and plays the assistant over `/ws/audio`. A tap anywhere starts the conversation, an end button ends it, payment ends it by itself. The laptop mode stays as it was. | The team shows the demo on a phone. The API key and all logic stay on the laptop. Chrome allows the microphone only over HTTPS; a certificate the phone warns about once needs no cable and no Chrome flags. No echo cancellation: a handset. An end button, not a tap anywhere, so a customer pointing at the screen does not end the order. |
| Echo gate | Off by default (`audio.echo_gate_rms`); when set, quieter microphone audio is sent as silence while the earpiece plays. | A handset (or earbuds with a separate mic) does not leak; open speakers might make the assistant interrupt itself. |
| The phone's covered edges | In phone mode the choices, the order and the prompts keep out of the edges the case covers (`phoneInsets`, % of the screen, in the developer panel; default 4.8 / 22.2 / 2.6 / 2.6 % for 1.5 / 7 / 0.5 cm of the team's 19.5 × 31.5 cm screen). The avatar is not moved; the order goes above its head. Choices taller than their place shrink to fit (all modes). | The team's case covers most of the bottom, where the order was. Measured roughly, so adjustable without code. |
| Background noise | `audio.noise_gate_rms` (off by default): quieter microphone audio is sent as silence, held open 0.5 s after louder audio. The phone's automatic gain is off. The developer panel shows the microphone's RMS. | Team test on the phone: the assistant reacted to noise around it. A handset keeps the voice much louder than the room; lowering the Live API's start sensitivity instead would miss short answers again (milestone 3). The value depends on the handset and the room, so it is measured there. |
| Server | FastAPI app started with `uv run python -m kiosk`: one WebSocket for displays, serves the built display and `data/images`. A `KioskController` connects the hook switch, the assistant session and the displays; full state snapshots on every change. | Simple and testable without a network (FastAPI test client, fake Live connection). A display can reconnect at any moment. |
| Developer events | The display sends `hook` (Space), `dev_text` and `dev_mute` over the same WebSocket; typing lifts the handset if needed. | Everything can be tested without a handset, through the real session. |
| Several items waiting | Items whose required options are missing wait side by side; `set_options` takes an `item_id`. | Found in the milestone 6 end-to-end test: "청포도 에이드 하나랑 아메리카노 하나" lost the ade when the americano was chosen. |
| One answer, several drinks | When the same item is being chosen more than once and the customer's answer does not say which one (or "둘 다"), it goes to the drink asked about and the kiosk asks "따뜻한 아메리카노도 레귤러로 해 드릴까요?"; the same answer put on another drink in the same turn is held until then. Questions and their order stay as they were. | Team test: an iced and a hot americano ordered together, "레귤러요" went to both. The team preferred checking an unclear answer over more detailed questions or a fixed order. |
| Prices for the model | In Korean words (`won_spoken`: "만 삼천이백 원") in everything the model reads or says; the screen keeps digits. | Team test: the model read "13,200원" as "십삼만 이천 원". |
| Partial answers recorded at once | A function result that asks for options tells the model to call `set_options` as soon as one answer comes. | The model otherwise waited for all answers, so the screen did not show "따뜻한" as chosen in between. |
| Customer subtitles | The customer's subtitle is the raw transcription of their words. | Showing the model's understanding instead was measured in milestone 8 ([live-check.md](live-check.md)): 0.2–0.4 s slower and the model wrote it only on half of the turns; kept for later. |
| Running the demo | Teammates download `voice-kiosk.zip` from the GitHub Releases page (the display already built) and double-click `Start Kiosk.bat`: it installs uv the first time, starts the kiosk and opens the display in an Edge window (`Start Kiosk (full screen).bat`: kiosk mode). A `v*` tag publishes the zip (`.github/workflows/release.yml`). | Most teammates do not use a terminal; the zip needs no Node.js and no git. |
| Avatar | A café employee stands behind everything and fills the screen: transparent WebM clips in `data/avatar/` (idle, pick up, listening, talking, put down) chosen by the kiosk's state; a still image until the clips exist. The orb is gone. | Team feedback (after milestone 8): a character feels like being served. WebM keeps transparency in Edge, so the background colour stays changeable. |
| Menu images | Empty at first; drop `data/images/<item_id>.png` (or jpg/webp). Placeholder: the item's emoji on a gradient. | Images will be AI-generated later; adding one needs no code change. |
| Developer mode | Typed Korean goes into the same Live session (audio can be muted). | Everything can be tested without a handset. |
| Architecture rules | `server` > (`assistant` \| `voice`) > `domain` > `config`; `domain` is pure. Enforced by `import-linter`. | Keeps the order logic testable and the audio/AI parts swappable. |
| Tests | No mic, speaker, network or browser; the Live session is mocked. | Carried over: runs in CI. |

## Gemini API, privacy and secrets

| Area | Decision | Reason |
|---|---|---|
| Free tier | Development on the free tier: ~15 requests/min and 500 requests/day per model for normal models; Live API limits are shown in AI Studio and measured in milestone 3. | Carried over (the old agent model hit the daily cap during testing). |
| Privacy: audio | The customer's voice and the conversation are sent to Google. On the free tier Google says the data is **used to improve its products**. Nothing is saved locally unless a developer turns recording on (git-ignored `recordings/`); logs hold text only (git-ignored `logs/`). | No local model is good enough on our PCs (old measurement: local 7B/14B models took 8–25 s per step). A real deployment would need the paid tier and a privacy notice. |
| Secrets | API key in `GEMINI_API_KEY` (environment or git-ignored `.env`), used by the backend only. Without a working key the display shows a form: the key typed there goes to the local backend (`POST /api/key`, accepted only from this computer), is checked with Google and saved to `.env`; it is never sent back to a display or logged. | Carried over; each teammate uses their own key. The form is for teammates who do not use a terminal or text editor. |
| Repo | **Public**, `jhj1012/voice-kiosk`. | Anyone can read the code and its history. Never commit API keys, `.env`, `*.local.yaml`, recordings or logs; a secret that was pushed once must be revoked. |
